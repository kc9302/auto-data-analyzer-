# 깃허브 브랜치 전략 및 AI 자동 코드 리뷰(PR) 머지 정책

## 1. 배경 및 목적
- **목적:** 개발 안정성을 보장하고, 지속적인 배포(CI/CD) 파이프라인에서 코드 품질과 보안 결함을 기계적으로 차단.
- **원칙:** 인간 리뷰어의 피로도를 줄이고, Karpathy 가이드라인(Think Before Coding, Simplicity First, Surgical Changes, Goal-Driven)을 GitHub Actions 상에서 기계적으로 강제.

---

## 2. 브랜치 흐름도 (Git Flow)

```
[main] ───────────────────────────● (정기 릴리즈 v2.3, v2.4...)
                                 ▲
                          (릴리즈 PR)
                                 │
[develop] ──────────●────────────● (통합 및 스테이징)
                    ▲
            (Grade A 필수 PR)
                    │
[feature/*] ────────┘ (기능 단위 독립 작업 브랜치)
[fix/*]
[refactor/*]
```

### 1) `main` 브랜치
- **성격:** 상용 배포(Production Ready) 전용 브랜치
- **보호 정책:** 직접 Push 금지. `develop` 브랜치에서 충분한 테스트 및 안정화가 완료된 후 릴리즈 PR을 통해서만 Fast-forward 머지.

### 2) `develop` 브랜치
- **성격:** 일상 개발 통합(Integration) 브랜치
- **보호 정책:** 모든 새로운 기능, 버그 픽스, 리팩토링은 `develop` 브랜치를 타겟으로 Pull Request(MR)를 생성해야 함.

### 3) 작업 브랜치 (`feature/*`, `fix/*`, `refactor/*`)
- `develop` 브랜치에서 생성:
  ```bash
  git checkout develop
  git pull origin develop
  git checkout -b feature/model-reproducibility
  ```
- 작업 완료 후 `develop` 브랜치로 PR 요청:
  ```bash
  git push origin feature/model-reproducibility
  ```

## 3. AI Quality Gatekeeper (머지 허용 기준)

PR이 `develop` 브랜치를 향해 열리거나 코드가 푸시되면 `.github/workflows/ai_code_reviewer.yml` 워크플로우가 자동으로 가동되어 **AI 코드 리뷰어(`.github/scripts/ai_reviewer.py`)**가 채점을 진행합니다.

### 📊 4대 정밀 평가 축 (100점 만점)
1. **Karpathy 원칙 및 수술적 변경 (30점):**
   - 변경된 코드 라인 수가 최소화(Surgical)되어 있는가?
   - 불필요한 공백, 무관한 파일 수정, 주석 처리된 레거시 코드가 없는가?
   - 코어 엔진(`src/`) 내 불필요한 `print()` 디버깅 구문이 배제되었는가?
2. **보안 및 개인정보(PII) 격리 정책 (25점):**
   - 소스코드 내 하드코딩된 API Key, Private Key, 비밀번호가 없는가?
   - 한국인 주민등록번호(RRN) 등 PII 패턴이 소스코드에 평문 노출되지 않았는가?
   - DB 접근 시 `validate_query` 규정을 준수하고 무해(Read-Only)한가?
3. **검증 가능성 및 자동화 테스트 (25점):**
   - 신규 기능 추가 시 `tests/` 디렉토리에 단위/통합 테스트가 동반되었는가?
   - `uv run pytest` 구동 시 전체 테스트(현재 23개)가 100% 통과(PASSED)하는가?
4. **아키텍처 및 모델 완벽 재현성 (20점):**
   - 모듈 간 의존성 결합도가 낮고, 단방향 흐름을 유지하는가?
   - 데이터 동결(`DataFreezer`) 및 고정 시드 원칙을 준수하는가?

## 4. 머지 게이트웨이 등급(Grade) 판격 규칙

| 종합 등급 | 획득 점수 | 치명적 결함(Critical) | 머지 허용 여부 | 조치 가이드 |
| :---: | :---: | :---: | :---: | :--- |
| **🏆 Grade A** | **90점 이상** | **0건** | **🟢 MERGE PERMITTED** | **머지 가능.** PR 코멘트에 칭찬 리포트가 등록되고 머지 버튼 활성화. |
| **⚠️ Grade B** | 80 ~ 89점 | 0건 | **🔴 MERGE BLOCKED** | **머지 차단.** 제안된 피드백 반영 후 추가 커밋 필요. |
| **⚠️ Grade C** | 70 ~ 79점 | 0건 | **🔴 MERGE BLOCKED** | **머지 차단.** 테스트 보강 및 수술적 변경 다듬기 필요. |
| **🚨 Grade F** | 70점 미만 | 1건 이상 | **🔴 MERGE BLOCKED** | **머지 차단.** 보안 위반, 테스트 실패 또는 대규모 결함 즉시 수정 필요. |

---

## 5. 로컬 사전 점검 방법

PR을 올리기 전 개발자가 로컬 터미널에서 리뷰 봇을 사전 구동해 자신의 등급을 미리 확인할 수 있습니다:

```powershell
# develop 브랜치 대비 내 변경점 리뷰 사전 실행
uv run python .github/scripts/ai_reviewer.py --base-ref origin/develop --out-report review_report.md
```
